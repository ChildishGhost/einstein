# RFCs

Every decision about Einstein starts here — new or changed behavior, interfaces, architecture, significant dependencies, the process. Fixes, refactors, dependency bumps and doc corrections need no RFC, but must not contradict one. The process is defined by [RFC 0001](0001-rfc-process.md); new RFCs start from the [template](0000-template.md).

## Workflow

1. **Draft** — run `/rfc-create <topic>` with a coding agent: you agree on the purpose, pick among options, then the agent grills the draft with you. By hand: `npm run rfc:new -- <kebab-title>`. Either way, add the `.zh-tw.md` translation.
2. **Accept** — you approve by running `/rfc-cascade NNNN`: `status: accepted`; failing tests citing each requirement (`RFC-NNNN/Rn`), except review-only ones marked *(manual)*; agent instructions in `AGENTS.md` and skills in `.claude/skills/`.
3. **Implement** — code until `npm test` and `npm run docs:check` pass.
4. **Document** — human docs in `README.md` and `docs/`, each with a `.zh-tw.md`.
5. **Verify** — the agent reports how each requirement is covered; you review, run `/rfc-cascade NNNN` again and confirm: `status: implemented`. Small decisions set `gates: accept` and skip this approval.

After you run `/rfc-cascade NNNN` on a draft, the agent carries it through stages 2–4 on its own. Only a human runs `/rfc-cascade`; agents cannot pass a gate. By hand, `npm run rfc:status -- NNNN <status>` changes a status.

Rules of thumb:
- An RFC cites only lower-numbered RFCs, and lists which earlier requirements it keeps or changes.
- Until an RFC is published (on `dev`, or in a non-draft pull request) it is amended in place. Once published: `accepted` RFCs only grow; `implemented` RFCs change only status and Errata.
- English is the source; translations carry the source's SHA-256 and are stale when it changes.
- *Retroactive* RFCs record decisions already in the code.
